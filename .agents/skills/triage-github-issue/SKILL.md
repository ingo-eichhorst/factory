# Triage and plan a Factory issue

Adapted from Irrlicht's `ir:triage`. Get an issue ready for
`implement-github-issue`. Diagnose it and make the design, testing and
process choices that implementation needs. Do not implement the fix, run
tests, or change files. Pass `--repo ingo-eichhorst/factory` to every `gh`
command.

## Invocation

- `/triage-github-issue #140`: triage one issue.
- `/triage-github-issue #140 #141`: triage several, one at a time.

If an issue already has an AI triage comment, edit that comment. Do not
add a second one. Start every comment with:

```text
> *This was generated by AI during triage.*
```

## Workflow

1. Assign the issue to the GitHub user on this machine, so everyone can
   see it is being worked on. Check that the assignment took:
   ```sh
   gh issue edit <N> --repo ingo-eichhorst/factory --add-assignee @me
   me="$(gh api user --jq .login)"
   gh issue view <N> --repo ingo-eichhorst/factory --json assignees \
     --jq "[.assignees[].login] | index(\"$me\") != null"   # must print true
   ```
2. Read the issue and all of its comments.
3. Read the code it cites, the tests near that code, the architecture
   boundaries in `README.md`, and `AGENTS.md`. Do not run tests or change
   files.
4. Check readiness and hard blockers.
5. Choose one high-level design and one testing strategy.
6. Set complexity, process, estimate and labels.
7. Post the assessment and apply the labels in one issue edit.

A dismissal such as "already fixed", "self-heals" or "not relevant" is an
assumption until code, a command or a cited PR verifies it. Mark an
unverified dismissal as assumed. Do not use it to shrink scope or risk.

## Readiness

Score each axis `✓` or `✗`, with one sentence of evidence.

| Axis | Pass condition |
|---|---|
| Scope | The affected behavior and likely components are bounded. |
| Specification | No external or hard-to-reverse decision remains. |
| Verifiability | A concrete signal can tell success from failure. |
| Observability | Existing or small new instrumentation can expose that signal. |
| Context | The relevant code and prior work are cited or easy to find. |
| Independence | No open issue, PR, credential or human decision blocks the work. |
| Reversibility | The change is local and can be reverted safely. |

Any failure gives `needs-info`, except an Observability failure whose cost
is low or medium. When the issue is bounded and reversible, the default is
`ready-for-agent`. Do not block on an implementation choice that can be
reversed; make that choice in the design.

Observability costs:

- **Low:** run an existing tool: a CLI command, `factory run log`, a
  metric, a snapshot, or the `shell` agent against a throwaway instance.
- **Medium:** extend an existing event, metric, fixture or test harness.
- **High:** build a new observation system. Give `needs-info` and name the
  prerequisite. Do not open a new issue without the maintainer's approval.

When the gap is Low or Medium, put the instrument it needs first in the
testing strategy.

If the issue pastes a test but never shows it failing on `main`,
Verifiability passes when the criterion is concrete, but mark it
**unproven**. Mark tests that only preserve existing behavior as **locks**.

Use `wontfix` only for a verified duplicate, an invalid report, or an
out-of-scope request. Explain why in one paragraph with evidence.

## High-level design

For a `ready-for-agent` issue, write a short list that settles:

- the intended behavior and the component boundaries (which crate:
  `factory-core`, `factory-plugins`, `factory-daemon`, `factory-cli`, or
  `ui/`);
- the data or control flow;
- the surfaces affected: CLI, HTTP, UI, the agent guide and the reporting
  contract;
- compatibility, permission and persistence constraints: serde defaults on
  stored rows, the grant in `access.rs`, the rules in `AGENTS.md`;
- what is explicitly left out.

Follow the patterns already in the repository. Choose one direction and do
not list alternative designs. The design is a strong default for the
implementation, not a file-by-file plan.

## Testing strategy

Write a short list naming exact tests, fixtures, commands, UI checks or
observable outputs (`cargo test -p factory-daemon workflows::`,
`cd ui && npm test`, a throwaway instance with the `shell` agent).
Classify each proof:

- **red-first:** a defect test that must fail before the fix;
- **lock:** a test of existing behavior that passes before and after;
- **mutation:** a new guard, rule, migration or contract check that must
  fail when the condition it protects is deliberately broken;
- **manual:** a physical or UI check that a person must perform.

Never claim that a test you have not run proves a defect. Mark it
**unproven**.

## Complexity and process

Start from the expected touch points. Add one level for one real design
uncertainty, or two for several. Cap the result at 10.

| Level | Expected change |
|---|---|
| 1–2 | One file or one unambiguous local fix. |
| 3–4 | One function or a small two-file extension. |
| 5–6 | One established slice across two to four files. |
| 7–8 | Cross-cutting, schema, trait-boundary or CLI/HTTP/UI-parity work. |
| 9–10 | A subsystem or a multi-phase change. |

Level 9–10, an unbounded issue, or level 7–8 without a phase boundary gives
`needs-info`. Ask the reporter or maintainer to split or bound it. Do not
invent child issues.

| Level | Investigation | Review |
|---|---|---|
| 1–2 | direct read | low |
| 3–4 | 1 Explore, medium | low |
| 5–6 | 1–2 Explore, medium | medium |
| 7–8 | 2–3 Explore, thorough | high |

## Estimate

Report agent-active time and human gates separately:

| Level | Agent-active time |
|---|---|
| 1–2 | 15–45 min |
| 3–4 | 45 min–2 h |
| 5–6 | 1.5–3 h |
| 7–8 | 2.5–5 h |

Change a range only for a named driver you observed. List each gate and
who owns it, for example a credential, a physical action, or a person
accepting the UI by eye.

## Labels

Apply one category: `bug` for broken behavior or a regression,
`enhancement` for new behavior, a refactor or polish, or `documentation`
when only documentation changes.

Apply one state: `ready-for-agent`, `needs-info` or `wontfix`. Remove any
other state label that is already there.

Add the area labels that apply, with a reason for each: `policy`,
`process`, `infrastructure`, `cost`, `quality`, `intake`, `direction`,
`accessibility`. Use `good first issue` only for level 1–2 local work.
Use `duplicate` or `invalid` only for a verified dismissal. Do not create
new labels.

## Assessment format

```markdown
> *This was generated by AI during triage.*

## Triage Assessment

**Category:** <bug | enhancement | documentation> — <reason>
**Priority:** <High | Medium | Low> — <reason; ready only>
**Areas:** <labels> — <reason; optional>
**Complexity:** <effective> (base <n>, uncertainty +<n>) — <reason>
**Process:** investigation <direct | 1 Explore | 1–2 Explore | 2–3 Explore> · review <low | medium | high>
**Estimate:** <range> agent-active · gates: <none | gate and owner> — <driver>

**Readiness:**
- ✓/✗ **Scope** — <reason>
- ✓/✗ **Specification** — <reason>
- ✓/✗ **Verifiability** — <reason>
- ✓/✗ **Observability** — <reason, and the cost when it fails>
- ✓/✗ **Context** — <reason>
- ✓/✗ **Independence** — <reason>
- ✓/✗ **Reversibility** — <reason>

## High-level design

- <chosen design point>

## Testing strategy

- <classification: exact proof and command>

**Verdict:** ready-for-agent | needs-info | wontfix

<!-- needs-info only -->
**Blocked on:**
- <one specific action and its owner>
```

For `needs-info`, leave out Priority, Process, Estimate, the design and the
testing strategy when a blocker keeps those choices from being valid.

```sh
gh issue comment <N> --repo ingo-eichhorst/factory --body-file assessment.md
# or, when re-triaging, edit the earlier AI triage comment instead:
#   gh api -X PATCH repos/ingo-eichhorst/factory/issues/comments/<id> -F body=@assessment.md
gh issue edit <N> --repo ingo-eichhorst/factory \
  --add-label <category>,<state>[,<area>...] \
  --remove-label <obsolete-state-labels>
```

## In a Factory run

The verdict decides the report, and the report decides what the workflow
does next:

- `ready-for-agent`: `factory task report --status done`. Put in
  `--result` the issue number and title, the complexity and process, the
  high-level design, the testing strategy, and the comment's URL.
  Implementation starts from that result.
- `needs-info` or `wontfix`, or anything you cannot settle yourself:
  report `--status blocked` with the specific question and who has to
  answer it. That puts it in front of a person. When they answer, triage
  again with the answer and report again.
